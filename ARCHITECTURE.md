# Architecture

## Data model

The core split is `makes` → `models` → `vehicles` → `listings`. Make and model are reference data, not strings on the listing: a normalized `models(make_id, name)` with a unique constraint per make means "BMW 3 Series" exists once, so the make and model filters are equality joins on indexed foreign keys instead of text matching, the dependent make/model selects in the filter sidebar are a single `GET /api/meta` read, and a renamed model does not fan out across hundreds of rows.

Vehicle and listing are separate because they change for different reasons and are queried differently. A vehicle carries physical facts (body type, fuel type, transmission, colour, mileage, power, doors, seats, first registration, next inspection) that are stable and heavily filtered on. A listing carries commercial facts (title, description, price, status, timestamps, seller) that change often. `listings.vehicle_id` is UNIQUE, so the relationship is one-to-one today, but the seam is where a "same car relisted" or vehicle-history feature would attach without reshaping the listing table. Images, saves and inquiries hang off the listing with `ON DELETE CASCADE`, so deleting a listing needs no application-side cleanup.

Index strategy follows the query shapes rather than the columns. Default browse is `status = 'ACTIVE'` ordered by `created_at DESC`, so `listings(status, created_at DESC)` serves the filter and the sort from one index. `listings(price_eur)` backs the price sorts and range filter, `listings(seller_id)` backs the seller dashboard. On the vehicle side every filterable dimension is indexed individually (`model_id`, `mileage_km`, `power_kw`, `first_registration`, `fuel_type`, `transmission`, `body_type`) because filters are freely combinable and the planner picks per query; a single composite would only help one column order. `models(make_id)` supports the make join, `saved_listings(listing_id)` and `inquiries(listing_id)` support the per-listing counts on the seller dashboard.

All filtering and sorting happens in SQL through JPA Specifications that join listings → vehicles → models → makes. Nothing is loaded and filtered in memory, which is what keeps the search honest as row counts grow.

## API surface

Everything is under `/api`. Public reads: `GET /api/listings` (the search endpoint, all parameters optional and combinable, repeated values OR within a dimension and AND across dimensions, paged), `GET /api/listings/facets` (same filters, returns counts per dimension computed with that dimension's own filter excluded), `GET /api/listings/{id}`, `GET /api/meta` for the filter UI, and `GET /api/images/seed/{vehicleId}-{n}.svg` which renders deterministic vehicle SVGs so the repository holds no binaries. Authenticated reads and writes: `/api/saved`, `POST /api/listings/{id}/contact`, listing CRUD under `/api/listings`, image upload and delete under `/api/listings/{id}/images` and `/api/images/{imageId}`, the seller views `/api/seller/listings` and `/api/seller/inquiries`, and the moderation endpoints under `/api/admin/**`. Errors are uniform JSON `{status, message, fieldErrors?}` from a `@RestControllerAdvice`, with bean validation on every request body.

## Auth model

Session-cookie authentication via Spring Security with BCrypt password hashing and three roles, `BUYER`, `SELLER` and `ADMIN`. `POST /api/auth/register` and `/api/auth/login` establish the session, `/api/auth/me` rehydrates the client on reload, `/api/auth/logout` clears it. The browser sends the cookie automatically, and in Docker the SPA and the API share an origin because nginx proxies `/api` to the API container, so no CORS configuration and no token storage in JavaScript. Authorization is layered: the filter chain permits browse, detail, meta, facets and images anonymously, requires authentication for saved listings and contact, requires `SELLER` for listing writes and `ADMIN` for `/api/admin/**`; ownership is then checked in the service layer, because a role alone does not entitle a seller to edit another seller's listing. CSRF is disabled deliberately for the prototype and is the first thing to restore before any real deployment.

## Modernizing a legacy marketplace onto this architecture

The realistic version of this project is not a greenfield launch, it is an existing marketplace with live traffic, a legacy database and a monolith nobody wants to freeze for six months. A big-bang cutover trades a known-mediocre system for an unknown one on a single date, with no rollback smaller than "restore last night's dump". The alternative is a strangler fig: put a routing seam in front of the legacy application, move one capability at a time behind it, and let the new stack grow into the traffic while the old one keeps serving everything it still owns.

### 1. Establish the seam

Put a reverse proxy in front of the legacy application first, before writing any new code. In this repository that role is already played by `frontend/nginx.conf`, which resolves `/api` to the API container and everything else to the SPA. In a migration the same file gains a third upstream: `location /api/listings` to the new Spring Boot service, everything else to `legacy_upstream`. Nothing behaves differently on day one, which is the point. The proxy is deployed, observed and rolled back on its own, so by the time it carries real routing decisions it is already boring.

### 2. Carve out read-only search first

Search is the right first slice because it is read-only, high value and easy to compare. The new stack owns `GET /api/listings`, `GET /api/listings/facets` and `GET /api/meta`; write paths, checkout, messaging and account management stay legacy. Run it dark to start: the proxy mirrors a percentage of search traffic to the new endpoint, discards the response, and a comparison job checks result IDs and total counts against the legacy query for the same parameters. Differences here are almost always mapping bugs, for example a legacy `fuel` column holding `Benzin` and `benzin` where this schema requires `PETROL`, or NULL mileage that the legacy list silently treats as zero. Fix them while nobody is looking at the output. When agreement holds, flip the proxy for one percent of search traffic, then ten, then all, watching p95 latency and result counts at each step. Rollback is a proxy config change, not a deployment.

### 3. Sync the legacy data into the new schema

Search cannot be served without data, and the new schema is not the legacy one. Build a one-time backfill that reads the legacy listing table and writes `makes`, `models`, `vehicles` and `listings`, doing the normalization work as it goes: insert-if-absent on `makes(name)` and `models(make_id, name)` (the same path `POST /api/listings` already uses for unknown make and model names), map the legacy fuel, transmission and body vocabularies onto this schema's uppercase enum values, and split each legacy row into its vehicle facts and its listing facts. Rows that fail to map go to a quarantine table with the reason rather than being dropped; the quarantine count is a migration KPI that has to reach zero before the write path moves.

For ongoing sync, prefer change data capture over dual writes. Logical replication out of the legacy PostgreSQL into a transform consumer that applies the same mapping keeps the legacy application untouched, survives writes made by cron jobs and admin scripts that bypass the application, and gives replay from a known LSN when the mapping changes. Dual write from the legacy application is the fallback when CDC is not available, and it needs an outbox table rather than a second in-request write, so a failed write to the new store cannot fail a user's listing update or silently diverge. Either way the sync is one-directional while the legacy side still owns writes, which keeps conflict resolution out of the picture entirely.

### 4. Bridge sessions and identity

The new endpoints must recognize users the legacy application logged in, or the first authenticated slice breaks. Two workable bridges: have the new service read the legacy session store directly (a shared Redis or session table) behind a `SecurityFilterChain` that maps a legacy session into the same `BUYER`/`SELLER`/`ADMIN` authorities used here, or have the legacy application issue a short-lived signed token that the new service verifies. Passwords migrate lazily: copy the legacy hashes into `users.password_hash`, and if the legacy algorithm is not BCrypt, verify with the legacy algorithm on first successful login and rehash with BCrypt in place, so no user is ever forced to reset. Keep one system authoritative for identity for the whole migration and treat the other as a reader.

### 5. Move write paths feature by feature

Once search is fully served by the new stack and the read model is trusted, move writes one endpoint at a time, each behind its own feature flag rather than one global switch. A sensible order is saved listings, then contact and inquiries, then listing create, update and delete, then moderation. Saved listings and inquiries first because they are self-contained, append-only and cheap to reconcile if a record is lost. Listing writes are the hard slice, because the moment `POST /api/listings` and `PUT /api/listings/{id}` write to the new schema, the new store becomes authoritative for that listing and the sync direction has to reverse for it. Handle that per listing rather than globally: an ownership marker on the listing decides which system may write it, migrated listings write to the new store and replicate back to legacy for as long as legacy pages still read them, and unmigrated listings continue as before. Flags are per endpoint and per cohort, so a bad listing editor affects internal staff or one percent of sellers rather than the whole seller base.

Image handling migrates alongside listing writes. New uploads go to `UPLOAD_DIR` (an object store in production) and produce `/api/images/upload/{filename}` rows in `listing_images`; legacy image URLs are copied as-is into the same table so the detail gallery renders a mixed set without caring which system produced it.

### 6. Retire legacy routes

Every route the proxy has fully cut over gets a hard 404 in the legacy application, not a quiet deletion. Traffic to a supposedly dead legacy route is the signal that something (a mobile client, a partner integration, an internal tool) still depends on it, and a 404 with a log line finds that in hours instead of during the eventual server decommission. When the legacy write path for a table has been dark for a full billing or reporting cycle, drop the sync job for it, then the legacy table, then the code. The migration ends when the proxy's `legacy_upstream` block has no `location` left pointing at it, at which point the proxy config is what this repository already ships.

### Rollback at each step

Each step has a rollback that is smaller than the step. Proxy routing reverts by config change, seconds, no deployment. A read slice reverts by flipping the same route back to legacy, and because reads have no side effects nothing needs repairing. A write slice reverts by turning off its feature flag and replaying the outbox or CDC stream in the other direction for the affected rows, which is only tractable because ownership is tracked per listing and every synced row keeps its legacy identifier. Schema changes deploy expand-then-contract: add the nullable column, backfill, dual read, only drop the old column once no code path reads it, so no single deploy is unrevertable. The rule throughout is that no step may put the system in a state where the only way forward is forward.
